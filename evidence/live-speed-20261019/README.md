## 已证实的三个因素

1. **模型动作本身小**：scene002第101–200步末端每步中位移动0.261mm，第201–300步0.357mm，且到第361步才把目标碗抬高2cm。因此不能单纯归因于渲染卡顿。动作XYZ的模长是归一化控制请求，不是米/秒。
2. **实际界面推进低于物理标称速度**：800步对应20Hz下40秒物理时间，但运行到保存约164秒。界面代码等待后台推理期间仍每轮重建两路相机观测；隔离假环境20次等待轮询实际触发20次观测重建、0次物理步。每步后另设置50ms等待，下一轮请求不是与此前推理重叠；Tk回调结束后再等30ms。这证明额外工作/等待存在，**尚不能量化真实渲染与推理各自占比**。
3. **任务完成后仍继续观察**：scene002首次连续10步释放撤手在643步，仍执行157步至800上限，末100步每步中位移动0.139mm。scene001首次327步后仍执行65步。这里连续10步只是事件，不自动等同于此前实验要求的额外50步严格跟进通过；当前交互模式也不以该事件停止。

800是停止上限，不是动作幅度或速度参数；此次确实跑满800。没有证据支持“再延长上限即可变快”或“训练久一点必然解决”。

## 不能从旧数据得出的结论

GUI动作CSV没有每步推理、物理、渲染时间，run→saved还含保存/编码，不能把164秒全部称为推理耗时。当前GPU闲置/P8采样发生在暂停期，不能当作运行时GPU瓶颈证据。两路相机重复重建的实际毫秒成本尚未单独测量。模型输出微小动作的学习层根因（示范、采样、预算或状态歧义）也未被本次只读检查唯一分离。
